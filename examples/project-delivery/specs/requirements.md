# 需求规格

阶段：`requirements`（需求分析师）· 产物：`specs/requirements.md`
优先级图例：`M` Must（必须有）· `S` Should（应该有）· `C` Could（可以有）· `W` Won't（本期不做）

---

## 1. 背景与目标

### 1.1 背景
企业需要对产品实现「一物一码」管理：为每件最小销售单元分配一个全局唯一追溯码，作为产品的「电子身份证」。追溯码编码遵循 GS1 结构（企业前缀 + 商品代码 + 序列号 + 校验位），用于唯一标识单件产品，并支撑按码快速核对该产品的基本信息。

### 1.2 目标
构建一个「追溯码管理服务」，提供两大核心能力：
1. **批量生成唯一追溯码**：可按商品一次性生成一批唯一追溯码，码随附该商品的产品信息（产品名、批次、生产日期），并可导出（CSV/文本）与持久化保存。
2. **按码查询产品信息**：输入追溯码，返回该码对应的产品名、批次、生产日期及码本身等元信息。

### 1.3 成功标准
- 生成的追溯码在同一商品维度下全局唯一。
- 一次批量调用即可生成指定数量并通过校验的追溯码，且可下载。
- 已生成并持久化的追溯码，可通过查询接口准确返回其产品信息。

## 2. 角色与场景（用户故事，含优先级）

### 2.1 角色
- **生产/仓库运营人员**：向系统提交商品与批次信息，批量申请生成追溯码，并导出码表用于生产贴标。
- **质量/追溯查询人员**（含后续消费者扫码场景）：输入追溯码，核对产品信息。

### 2.2 用户故事

**US-1 按商品批量生成追溯码**（`M`）
> 作为<生产/仓库运营人员>，我希望<按商品批量生成一批唯一追溯码，并绑定产品名/批次/生产日期>，以便<为每件产品分配唯一身份并完成贴标赋码>。

**US-2 导出已生成的追溯码**（`S`）
> 作为<生产/仓库运营人员>，我希望<把本批生成的追溯码下载为 CSV/文本码表>，以便<离线打印或导入贴标设备>。

**US-3 按码查询产品信息**（`M`）
> 作为<质量/追溯查询人员>，我希望<输入一个追溯码即可查询该码对应的产品名/批次/生产日期及码本身>，以便<快速核对产品溯源信息>。

**US-4 查询非法或未生成的码**（`S`）
> 作为<质量/追溯查询人员>，我希望<当我输入一个无法通过校验或系统中不存在的码时得到明确提示>，以便<区分有效标注与输入错误>。

## 3. 功能需求（逐条，含 Given/When/Then 验收标准）

### FR-1 批量生成唯一追溯码（`M`）
**描述**：服务支持按商品批量生成唯一追溯码。调用方需提供企业前缀、商品代码、批次、生产日期、生成数量，以及产品名绑定信息。每个码由「企业前缀 + 商品代码 + 序列号 + 校验位」构成，同一商品代码下序列号唯一。

**验收标准**：
- Given 一个合法商品代码（企业前缀 + 商品代码）、生成数量 N 与产品信息（产品名、批次、生产日期），When 调用批量生成接口，Then 返回 N 个互不重复的合法追溯码。
- Given 同一商品代码连续两次批量生成，When 对比两批结果，Then 两批码之间任意两个码都不相同（全局唯一）。
- Given 生成的每个追溯码，When 按公司前缀+商品代码+序列号计算校验位，Then 校验位与码中校验位一致（通过合法性校验）。
- Given 生成接口入参缺失或非法（如数量为 0、负数、超过上限，或企业前缀/商品代码/批次为空），When 发起请求，Then 返回明确参数错误且不生成任何码。

### FR-2 生成时绑定并持久化产品信息（`M`）
**描述**：生成追溯码时，将产品名、批次、生产日期作为入参与码一起持久化保存，供后续按码查询使用。

**验收标准**：
- Given 一次批量生成含产品名 A、批次 B、生产日期 D，When 生成完成，Then 生成的每个码保存时都关联产品名 A、批次 B、生产日期 D。
- Given 已生成并保存的追溯码，When 查询该码，Then 返回的产品名/批次/生产日期与生成时绑定的入参一致。

### FR-3 导出追溯码（`S`）
**描述**：服务支持将本批生成的追溯码导出为可下载的码表（CSV/文本）。

**验收标准**：
- Given 一批已生成的追溯码，When 调用导出接口，Then 返回可下载文件，内容包含该批全部追溯码（含绑定产品名/批次/生产日期列）。
- Given 导出的文件，When 逐行读取，Then 每行码可通过合法性校验且不重复。

### FR-4 按码查询产品信息（`M`）
**描述**：服务支持输入追溯码查询其产品信息，返回码本身、产品名、批次、生产日期。

**验收标准**：
- Given 一个有效且已持久化的追溯码，When 调用查询接口，Then 返回该码本身、产品名、批次、生产日期。
- Given 输入一个校验不合法（如长度错误或校验位错误）的码，When 调用查询接口，Then 返回明确提示「无效追溯码」而非正常业务数据。
- Given 输入一个合法但系统不存在（未生成）的码，When 调用查询接口，Then 返回「未找到对应产品」提示。

### FR-5 查询性能（`M`）
**描述**：按码查询应在参考数据量下保持可接受的响应速度。

**验收标准**：
- Given 系统已持久化待查询码，When 单个按码查询，Then 在参考数据量下响应时间不超过 500ms（参考值，可视部署规模调整）。

## 4. 非功能需求

- **准确性与唯一性**：追溯码在相同商品维度下必须全局唯一；校验位计算必须严格符合公司前缀+商品代码+序列号规则，杜绝重复与冲突。
- **可用性**：批量生成与按码查询接口需提供明确、结构化的错误返回（参数错误、校验失败、未找到等），便于调用方处理。
- **持久性与可审计**：已生成码及绑定产品信息需持久化保存；生成记录应可追溯（含生成时间、商品、数量、批次）。
- **扩展性**：序列号长度/批量上限应可配置，以适应不同企业的容量需要；可扩展支持不同码载体（后续）。
- **安全性**：查询与生成接口应按需鉴权，避免未授权访问码数据（默认门禁）。

## 5. 范围外与约束

- 本期**不包含**：完整全链路追溯（仓储/物流/销售事件）、防窜货区域告警、防伪码查询次数校验、营销（扫码领红包）、箱码/垛码层级关联、消费者扫码 H5 页面。
- 本期**不做**：从 ERP/WMS/MES 等异构系统的数据集成与增量同步。
- **约束**：编码遵循 GS1 结构（企业前缀+商品代码+序列号+校验位）；同一商品代码下序列号唯一即保证「一物一码」。
- **依赖**：需企业前缀、商品代码、序列号段的有效配置作为生成前置条件（相关配置管理可作为后续功能，本期假定调用方直接提供这些入参）。

## 6. 风险与待确认问题

- **R1 唯一性保障**：并发批量生成时如何保证序列号不冲突，需在生成层做幂等/加锁或基于数据库唯一约束兜底。
- **R2 校验位口径**：校验位采用的具体算法（GS1 检查码规则）需在实现阶段固定并做单元验证。
- **R3 存储选型**：持久化采用的关系/键值存储及索引策略影响查询性能，需在设计与实现阶段确认。
- **Q1**：批量生成单次数量上限建议值待确认（当前假定一个可配置上限，如 10,000）。
- **Q2**：查询返回展示形式（API JSON 即可）本期即满足，消费者扫码 H5 在范围外。
